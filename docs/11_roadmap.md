# 11. Дорожная карта

Жёстких приоритетов нет: MVP делается подробно и целиком, в удобном порядке. Ниже **рекомендуемая последовательность**, потому что последующие этапы опираются на предыдущие. Сроки не фиксированы. Для каждого этапа бэкенд делается раньше соответствующего экрана (контракт API → типы → интерфейс).

## Этап 0. Фундамент и «тонкий срез»
**Цель:** проверить всю цепочку от кнопки в Telegram до данных в БД и убрать главный технический риск.
- [ ] Репозиторий; бэкенд: `pyproject.toml` (uv), Ruff, MyPy strict, pytest, pre-commit.
- [ ] Структура папок (`03`), `core/` (config, logging, exceptions, texts, timeutils).
- [ ] Docker Compose для local (postgres, redis, MinIO). Alembic, сессии БД, Unit of Work.
- [ ] `main.py`: FastAPI + lifespan + `/health`; каркас Aiogram; Sentry.
- [ ] Фронтенд: `frontend/` (Vite + React + TypeScript strict), ESLint, Prettier, Vitest, Tailwind, shadcn/ui, прокси на бэкенд.
- [ ] Генерация типов: `pnpm gen:api` и проверка актуальности в CI.
- [ ] Серверные сессии в Redis, `POST /auth/telegram` с проверкой `initData`, `GET /me`.
- [ ] **Прототип в Telegram:** страница «Привет, {имя}» через `web_app`-кнопку; проверить на iOS и Android: загрузка, cookie, тема, кнопка «Назад». Если cookie блокируются, перейти на запасной вариант (`03`, раздел 7).
- [ ] CI: бэкенд и фронтенд (lint, типы, тесты, сборка).

## Риски и меры

| Риск | Вероятность | Влияние | Мера |
|---|---|---|---|
| Ограничения Telegram в РФ | Высокая | Критическое | Прокси (`TELEGRAM_PROXY_URL`/`TELEGRAM_API_BASE`); веб-вход по ссылке в браузере; `Notifier` как интерфейс для замены канала (MAX); накопление уведомлений в outbox; фронтенд без внешних зависимостей |
| Cookie не работают в WebView Telegram на части устройств | Средняя | Среднее | Прототип на этапе 0 на iOS и Android; запасной вариант с токеном в памяти (`03`, п. 7) |
| Недостаток опыта с TypeScript/React | Высокая | Среднее | Подробное руководство `12`, строгие правила для агентов (`06`, часть B), малые шаги, автопроверки в CI |
| Рассинхронизация фронтенда и бэкенда | Средняя | Среднее | Типы генерируются из OpenAPI, проверка в CI |
| Ошибки в расписании при смене часовых поясов/DST | Средняя | Среднее | Хранение UTC, шаблоны с IANA-поясом, тесты на переход времени |
| Устаревшие шкалы экзаменов | Высокая (ежегодно) | Среднее | Шкалы в БД с `valid_year`, ежегодная проверка (`10`, п. 11) |
| Потеря данных | Низкая | Критическое | Ежедневные бэкапы + проверка восстановления |
| Юридические требования по ПДн | Средняя | Среднее | Чек-лист `09`, данные в РФ, консультация юриста перед расширением |
| Сложность групповых уроков | Средняя | Среднее | Схема с `lesson_participants` с самого начала, тесты |

## Определение «MVP готов»
1. Этапы 0–7 выполнены, тесты зелёные (бэкенд и фронтенд).
2. Сценарий «приглашение → вход → расписание → ДЗ → оценка → уведомления» проходит на staging без ручных правок БД.
3. Владелец ведёт реальное расписание и ДЗ ≥ 10 учеников две недели без критичных сбоев.
4. Бэкап восстановлен успешно.
5. Все экраны соответствуют `07_design.md` (если заполнен).
6. Приложение проверено на реальных iOS и Android в Telegram и в браузере на десктопе.

# MY_LMS («Ромчик | ИнфоМат») — план создания проекта с нуля

> **Версия:** 2.0 · **Дата:** 05.10.2026
> **Для кого:** владелец проекта (не разработчик) и два локальных агента.
> **Что это:** пошаговый план «пустая папка → MVP → полная версия». Для каждой задачи есть **готовый промпт**, который вы копируете агенту, и **способ проверки**, который вы можете выполнить сами.

# 1. Как всё устроено

## 1.1. Роли

| Метка | Кто | Что делает | Чего не делает |
|---|---|---|---|
| 💻 **CODE** | Локальный агент-программист (Qwen Code) | Пишет файлы: Python, TypeScript, миграции, тесты, конфиги Docker/CI/nginx, документацию | Не запускает деплой, не лезёт в боевые данные, не добавляет библиотеки без вашего согласия, не придумывает правила бизнеса |
| 🖥️ **TERM** | Локальный агент-терминал (OpenCode) | Git и GitHub (`gh`), установка инструментов, `uv`/`pnpm`, Docker, запуск проверок, миграции, туннель, сервер, деплой, бэкапы | **Не правит код.** Красная проверка → отчёт возвращается CODE |
| 👤 **OWNER** | Вы | Создать репозиторий и бота, вставить секреты, проверить с телефона, принять решение, нажать Merge | — |

## 1.2. Цикл одной задачи (ваша «рутина»)

```text
1. Вы   → TERM: промпт «СТАРТ» (§3.2)          → рабочая ветка сбрасывается на актуальный main (новые ветки не создаются)
2. Вы   → CODE: промпт задачи из этого плана   → CODE пишет код + тесты, выдаёт отчёт
3. Вы   → TERM: промпт «ФИНИШ» (§3.3)          → TERM запускает проверки, коммитит, пушит, открывает PR, ждёт CI
4. Вы   проверяете по блоку «Проверка» задачи (§4) → нажимаете Squash and merge (рекомендуется для чистой истории; технически не ограничено)
5. Вы   → TERM: «Задача влита, вернись на main и обнови» → СТОП, следующая задача
```

Красная проверка на шаге 3: TERM показывает лог → вы пересылаете лог CODE промптом «ИСПРАВЛЕНИЕ» (§3.4) → снова шаг 3. **Не более 3 кругов**, потом остановка и вопрос вам.

Чисто TERM-задачи (установка, Docker, сервер) идут **без** шагов 2–3: вы даёте TERM промпт из блока задачи.
Чисто OWNER-задачи — шаги в блоке задачи.

> **Правило веток (решение владельца):** отдельная ветка под каждую задачу **не создаётся**. Работа идёт в единственной рабочей ветке сессии, Pull Request открывается **сразу в `main`**. После merge рабочая ветка сбрасывается на актуальный `main`. Поле «Ветка» в блоках задач ниже — справочное, по нему ветки не создаются.

## 1.3. Как читать блок задачи

```text
### T1.07 · Название
Кто: 💻 CODE · Размер: S/M/L · Ветка: feature/t1-07-slug · Коммит: `feat(x): …`
Читать: docs …
Промпт: (готовый текст в блоке кода)
Проверка: 🤖 команды → ожидаемый результат; 👁 что посмотреть вам; 📱 что проверить в Telegram
```

Размер: **S** — меньше часа, **M** — несколько часов, **L** — большая; если агент не укладывается в один коммит, пусть сам предложит разбиение и остановится.

# 2. Принятые решения

|---|---|
| Основа | Строим **с нуля по `docs/`**. Старый код не переносим |

| Секреты | Токен бота и ваш Telegram ID вставляете **только вы** и **только** в локальный `.env.local`. Агентам, в чат и в Git — никогда |

| Бот | `@romchik_infomat_bot` — **один бот и для разработки, и для боя** (ADR 0009). Реальных учеников до запуска нет. **Перед боевым запуском (T9.10) токен обязательно перевыпускается (`/revoke`), а локальная разработка переходит на отдельный dev-бот** |
| Шкалы ЕГЭ/ОГЭ | Приняты владельцем как верные (ADR 0004); обновляются ежегодно |
| Юридическое (ПДн) | После реализации, но **до широкого запуска** (T9.12) |
| Тон интерфейса | Ученику «ты», персоналу нейтрально (`docs/07` приоритетнее `docs/05`) |

# 3. Универсальные промпты

Вставляйте как есть, подставляя значения в `<угловых скобках>`.

## 3.1. Первый промпт сессии CODE (один раз на новую сессию агента)

```text
Ты — CODE-агент проекта MY_LMS (репетиторская LMS в Telegram: бот + Mini App).
Первым делом прочитай целиком: QWEN.md (если файла ещё нет — docs/QWEN.md и docs/06_agent_rules.md), docs/00_README_INDEX.md.
Правила, которые действуют всегда:
- Документация в docs/ — источник истины. Ничего не придумывай: ни функций, ни полей, ни ролей. Если документы противоречат друг другу или данных не хватает — ОСТАНОВИСЬ и задай вопрос. Приоритет документов: 07 → 01 → 04 → 08 → остальные.
- Стек зафиксирован в docs/02. Новые зависимости — только с моего согласия.
- Одна задача за раз. Ветка уже создана. Не начинай следующую задачу.
- Слои бэкенда: api/bot/worker → services → repositories → db/models. Коммит транзакции делает только сервис.
- Всё время — только UTC (timestamptz). Тексты бота — только src/core/texts.py, тексты фронтенда — только src/lib/texts.ts.
- Секреты не пиши в файлы, логи и ответы. Никогда не открывай и не печатай .env.local.
- Пиши тесты вместе с кодом (включая негативные случаи). Не удаляй, не пропускай (skip) и не ослабляй существующие тесты, чтобы «позеленело».
- Не используй # type: ignore, @ts-ignore, any без письменного обоснования в отчёте.
- Ты НЕ запускаешь деплой, Docker на сервере, git push и команды с побочными эффектами в системе — этим занимается TERM-агент. Локально запускать тесты/линтеры можно.
- Идентификаторы и коммиты — по-английски, комментарии и тексты для пользователей — по-русски.
Подтверди, что прочитал, и жди задачу.
```

## 3.2. Промпт «СТАРТ» для TERM

```text
Ты — TERM-агент проекта MY_LMS: git, gh, Docker, uv, pnpm, запуск проверок, миграции, сервер. Ты НЕ правишь бизнес-код: красная проверка → возвращаешь лог, сам не чинишь.
Правила: секреты не печатать и не коммитить; перед опасными командами (rm -rf, drop, force-push, остановка сервисов, правка БД) спросить меня.
Старт задачи <ID>:
1) git fetch origin && git switch main && git pull --ff-only
2) git status — рабочее дерево должно быть чистым (если нет — остановись и покажи мне)
3) Новую ветку НЕ создавай: останься в рабочей ветке сессии (git checkout -B <рабочая-ветка> origin/main).
4) Выведи: текущую ветку, последний коммит main (hash + сообщение).
Больше ничего не делай и жди.
```

## 3.3. Промпт «ФИНИШ» для TERM

```text
Финиш задачи <ID> (ветка <имя>, сообщение коммита: "<тип(область): описание>").
1) git status и git diff --stat — покажи список изменённых файлов.
2) Запусти полную проверку: `uv run python scripts/check.py` (бэкенд + фронтенд). Если скрипта ещё нет — запусти по отдельности: ruff check, ruff format --check, mypy --strict src, pytest -q, а во frontend: pnpm lint, pnpm typecheck, pnpm test --run, pnpm build.
3) Если есть красное — покажи полный вывод ошибок и ОСТАНОВИСЬ (не чини код).
4) Если всё зелёное: проверь, что в diff нет файлов .env*, ключей, больших бинарников (gitleaks detect --no-git или по возможности pre-commit run --all-files).
5) git add -A && git commit -m "<сообщение>" && git push -u origin HEAD
6) gh pr create --fill --base main (PR сразу в main из рабочей ветки) (в описание вставь отчёт CODE-агента, который я тебе дам ниже) и затем gh pr checks --watch.
7) Выведи: ссылку на PR, итог CI (по шагам), число изменённых файлов/строк.
Не делай merge. Жди моей команды.

Отчёт CODE-агента:
<вставьте отчёт>
```

## 3.4. Промпт «ИСПРАВЛЕНИЕ» для CODE

```text
Проверка задачи <ID> упала. Исправь ТОЛЬКО причины ошибок ниже, не расширяй задачу и не ослабляй тесты. Если причина — в документации или тесте, объясни и спроси меня.
Лог:
<вставьте вывод TERM>
После исправления выдай обновлённый отчёт по формату (приложение B).
```

## 3.5. Формат отчёта CODE (требуйте его всегда)

```text
Задача: <ID>
Что сделано: 1–3 предложения простыми словами
Файлы: список создан/изменён и зачем
Тесты: какие добавлены; какие негативные случаи покрыты
Проверки, которые я запускал локально: команда → результат
Миграция: есть/нет; upgrade и downgrade проверены?
Контракт API изменился?: да/нет (обновлён ли docs/08)
Отклонения от документации / допущения / вопросы ко мне: …
Следующую задачу НЕ выполнял.
```

## 3.6. Промпт «РЕВЬЮ» (для независимой проверки; запускать в **новой** сессии)

Полезно для «рискованных» задач (безопасность, деньги, права доступа, время). Лучше запускать другой моделью/сессией, не той, что писала код.

```text
Ты — независимый ревьюер проекта MY_LMS. Ты ничего не меняешь, только читаешь.
Сравни изменения ветки <имя> с main (git diff main...HEAD) с документацией docs/ (особенно <перечень документов>).
Проверь и ответь списком «ОК / ПРОБЛЕМА» по пунктам:
1) Реализовано ровно то, что в задаче <ID>, ничего лишнего.
2) Нет нарушений слоёв (api → services → repositories), commit только в сервисах, нет aiogram в services.
3) Всё время UTC, нет datetime.now() без tz.
4) Права проверяются на сервере; в ответах ученику/менеджеру нет цен и финансов.
5) Нет секретов, нет логов с персональными данными.
6) Тесты: есть негативные, не отключены, проверяют поведение, а не только «вызвалось ли».
7) Нет скрытых «заглушек»: TODO, pass, raise NotImplementedError, возврат фиктивных данных.
8) Соответствие docs/04 (таблицы, ограничения) и docs/08 (эндпоинты, коды ошибок).
В конце дай вердикт: МОЖНО МЕРЖИТЬ / ДОРАБОТАТЬ (с перечнем).
```

# 4. Как проверять работу агентов

Вы не обязаны читать код. Проверка устроена в **четыре слоя**. Чем выше риск задачи, тем больше слоёв.

## 4.1. Слой 1 — автоматика (обязательно для каждой задачи)

Одна команда, которую запускает TERM (а вы можете запустить сами из корня проекта):

```bash
uv run python scripts/check.py
```

Скрипт (создаётся в T0.10) выводит таблицу:

```text
backend  ruff check ........ PASS
backend  ruff format ....... PASS
backend  mypy --strict ..... PASS
backend  pytest ............ PASS (42 passed)
frontend lint .............. PASS
frontend typecheck ......... PASS
frontend test .............. PASS
frontend build ............. PASS
ALL CHECKS PASSED
```

Правила:
- Любое `FAIL` → задача **не принимается**.
- На GitHub в PR должна быть **зелёная галочка** (CI). Красный крестик → не мержить.
- Число тестов должно **расти**. Если стало меньше — агент удалил тесты → «красный флаг».

## 4.2. Слой 2 — доказательство от TERM (команды на реальной системе)

Для задач с БД, Docker, файлами, уведомлениями TERM выполняет конкретные команды и показывает вывод. Каждая задача ниже содержит пункт «🤖». Требуйте **вывод команд**, а не слова «всё работает».

## 4.3. Слой 3 — ваш просмотр PR (5 минут, без чтения кода)

Откройте PR → вкладка **Files changed** и ответьте на вопросы:

| Вопрос | Красный флаг |
|---|---|
| Файлы относятся к задаче? | Правки в чужих модулях, файлы `docs/` изменены без причины |
| Есть ли файлы `tests/` или `*.test.ts(x)`? | Логика есть, тестов нет |
| Тесты не удалены/отключены? | `-` (красные строки) в тестах; `skip`, `xfail`, `.only` |
| Появились новые зависимости? | Изменения в `pyproject.toml` / `package.json` без вашего согласия |
| Нет секретов? | `.env`, строки вида `token=...`, длинные ключи |
| Нет «затычек»? | Поиск по PR (Ctrl+F): `TODO`, `FIXME`, `type: ignore`, `ts-ignore`, `any`, `NotImplemented`, `pass`, `console.log` |
| Размер PR разумный? | Тысячи строк в одной задаче → попросите разбить |

Три быстрых команды локально (после `git switch <ветка>`):

```bash
git diff --stat main...HEAD                       # список файлов и размер
git diff main...HEAD -- pyproject.toml frontend/package.json   # новые зависимости
git diff main...HEAD | grep -nE "TODO|FIXME|type: ignore|ts-ignore|: any|skip\(|\.only\("
```

## 4.4. Слой 4 — руками в Telegram/браузере (на воротах этапа)

В конце каждого этапа есть «Чек-лист приёмки владельца»: что нажать и что должно произойти. Это **главная** проверка: тесты доказывают, что код делает то, что задумал агент, а вы проверяете, что это то, что нужно вам.

## 4.5. Красные флаги поведения агента

- Говорит «готово», но не показывает вывод проверок.
- «Исправляет» красный тест, меняя ожидаемое значение или удаляя тест.
- Добавляет библиотеку «для удобства».
- Пишет `# type: ignore` / `any` «чтобы прошла типизация».
- Трогает больше файлов, чем нужно задаче; делает «заодно» следующий шаг.
- Придумывает поле/статус/правило, которого нет в `docs/`.
- Читает или печатает `.env.local`.

При любом флаге: промпт «ИСПРАВЛЕНИЕ» с точной претензией; при повторении — новая сессия агента и промпт 3.1 заново.

## 4.6. Что делать, если агент зациклился

После 3 неудачных кругов: остановитесь, откройте **новую** сессию CODE, дайте ей промпт 3.1 + описание задачи + последний лог, а также попросите «сначала предложи план из 3–5 пунктов, жди моего ОК». Если и это не помогло — задача слишком большая: попросите разбить на подзадачи.

# Этап P · Подготовка (делает владелец)

**Цель:** подготовить пустую папку, репозиторий, бота и инструменты. Агентов пока не запускаем (кроме T0.01).

### P.1 · Создать репозиторий на GitHub
**Кто:** 👤 OWNER
1. github.com → **New repository**.
2. Имя, например `LMS_TUTOR_TG` (или новое). Видимость: **Public** (на время разработки, решение принято).
3. **Не отмечайте** «Add a README», «.gitignore», «license» — репозиторий должен быть **пустым**.
4. Create repository. Скопируйте адрес вида `https://github.com/<вы>/<имя>.git`.

**Проверка:** на странице репозитория написано «Quick setup» и нет файлов.

### P.2 · Создать папку проекта и положить документацию
**Кто:** 👤 OWNER
1. Создайте папку, например `D:\projects\lms` (или `~/projects/lms`). Внутри — **пока ничего больше**.
2. Распакуйте архив `docs_bundle.zip` (приложен к этому плану) так, чтобы получилась папка `docs/` с файлами `00…12` и `QWEN.md` (его перепишет агент в T0.04).
3. Файл `PLAN_FROM_SCRATCH.md` (этот план) уже лежит в `docs/` внутри архива.

**Проверка:** в папке лежит `docs/` с файлами `00_README_INDEX.md … 12_frontend_guide.md`. Больше ничего.

### P.3 · Установить программы (если ещё нет)
**Кто:** 👤 OWNER (TERM проверит в T0.01)

## Приложение A. Типовые проблемы и что делать

| Симптом | Что делать |
|---|---|
| `docker compose up` ругается на порт занят | TERM: показать, кто занимает порт (`netstat`/`lsof`), предложить изменить порт в `.env.local`, не убивать чужие процессы без вашего ОК |
| `alembic upgrade` падает | TERM возвращает полный лог CODE; **ручной SQL в БД запрещён**; если БД локальная и тестовая — можно пересоздать том (`docker compose down -v`) с вашего разрешения |
| CI красный, а локально зелёно | Чаще всего: разные версии, забытый `uv.lock`/`pnpm-lock.yaml`, отсутствие service containers. TERM показывает версии и лог CI, CODE исправляет |
| Агент «починил», удалив тест | Красный флаг §4.5: промпт «ИСПРАВЛЕНИЕ» + требование вернуть тест |
| Бот молчит | TERM: `getMe`, `getWebhookInfo`, режим (`polling`/`webhook`), логи `app`; ошибки `last_error_message` — вернуть CODE |
| Mini App «белый экран» в Telegram | TERM: логи nginx/app, адрес туннеля поменялся? (`scripts/dev_tunnel`), `PUBLIC_BASE_URL`/Origin в `.env.local`; кнопка меню в BotFather на новый адрес |
| Токен бота попал в чат/Git | **Сразу** `/revoke` у BotFather, новый токен в `.env.local`; если коммит с токеном уже в Git — сообщите TERM (чистка истории или смена репозитория по ситуации) |
| Агент просит добавить библиотеку | Спросите: «зачем, чем нельзя без неё, есть ли в `docs/02`?» Согласие — запись в ADR |
| Агент зациклился | §4.6: новая сессия, план из 3–5 пунктов, ваш ОК |

## Приложение C. Условия остановки агента

Агент обязан остановиться и спросить вас, если:
1. Документы противоречат друг другу, или задача требует решения, которого нет в `docs/`.
2. Нужно добавить зависимость, сменить стек или архитектуру.
3. Для продолжения нужен секрет, доступ или оплата.
4. Команда необратима (удаление данных, force-push, правка боевой БД).
5. После 3 кругов проверки остаются красными.
6. Задача затрагивает несколько независимых модулей (нужно разбить).
7. Обнаружена утечка секрета или уязвимость.

# 06. Правила написания кода для ИИ-агентов: MY_LMS

Этот файл — системные правила. Соблюдайте их строго. Владелец проекта хорошо знает Python, но **почти не знает JavaScript/TypeScript**, поэтому код фронтенда должен быть простым, явным и подробно прокомментированным.

## 0. Перед началом любой задачи
1. Прочитайте документы `00`–`05`, `08`–`12`. Если `07_design.md` заполнен, прочитайте и его.
2. **Не придумывайте функционал, которого нет в документации.** Если что-то неясно или документы противоречат друг другу, остановитесь и задайте вопрос владельцу.
3. Не меняйте стек и архитектуру без согласования (`02`, `03`). Не добавляйте зависимости без согласования.
4. Если задача меняет данные или бизнес-правила, сначала предложите правку документации, затем код.
5. Делайте небольшие шаги: один модуль или экран за раз, с запуском проверок после каждого.

## 1. Общие правила
- **Язык:** идентификаторы (переменные, функции, классы, файлы), сообщения коммитов — **английский**. Комментарии и docstrings — **русский**.
- Сообщения коммитов: Conventional Commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`, `chore:`).
- Без «магических» значений: константы и enum в отдельных модулях.
- Никаких `print` / `console.log` в коммитах: только логгер (бэкенд) и Sentry (фронтенд).
- Не пишите «умный» код. Предпочитайте простой и очевидный.
- Секреты не хардкодятся. Реальные значения не коммитятся. При добавлении настройки обновляйте `.env.example` (бэкенд) и `frontend/.env.example`.

## Часть A. Бэкенд (Python)

### A1. Стиль и типизация
- **Python 3.11.** Type hints обязательны везде (**MyPy strict**). **Ruff** (lint + format).
- Docstrings в стиле Google, на русском.
- Функции короткие, с одной ответственностью. Сервисы — классы, зависимости передаются через конструктор.

### A2. Асинхронность
- Блокирующий I/O запрещён: `requests`, `psycopg2`, синхронный `boto3`, `time.sleep`.
- Используйте `httpx`, `asyncpg`, `aioboto3`, `aiofiles`, `asyncio`.
- CPU-тяжёлые операции (сжатие фото Pillow) выносятся в `asyncio.to_thread`.
- SQLAlchemy: только 2.0-синтаксис (`select()`, `AsyncSession`), без неявных ленивых загрузок (`selectinload`/`joinedload`).

### A3. Слои (см. `03`)
- Запросы к БД только в `repositories/`.
- Бизнес-логика только в `services/`. Сервисы не импортируют `aiogram` и `fastapi`.
- `api/`, `bot/`, `worker/` тонкие: разбор ввода → проверка прав → вызов сервиса → ответ.
- Отправка сообщений пользователям — только через интерфейс `Notifier`.

### A4. Транзакции и данные
- **Commit делает только сервисный слой.** Репозитории делают `flush`.
- Один метод сервиса = одна бизнес-транзакция. Побочные эффекты наружу (сообщения, S3) — после коммита или через `notifications` (outbox).
- Время: UTC (`timestamptz`), никаких наивных `datetime`; используйте `core/timeutils.py`.
- Деньги и баллы — целые числа.
- Любое изменение схемы = миграция Alembic с рабочим `downgrade`.
- Шкалы экзаменов, типы экзаменов, предметы — только данные в БД.
- В `audit_log` пишутся события из `04`, раздел 7.2.

### A5. Обработка ошибок
- Работа с БД, S3, Telegram API оборачивается в `try/except` на границах сервисов.
- Только кастомные исключения из `core/exceptions.py`. Не глотайте исключения молча.
- Ошибки уровня `ERROR` логируются с трейсбеком (`logger.exception`) без персональных данных (используйте идентификаторы).
- API возвращает единый формат ошибок из `08`.

### A6. API (FastAPI)
- Для каждого эндпоинта: Pydantic-схемы запроса и ответа, `tags`, `summary`, стабильный `operation_id`, модели для всех кодов ответа (от них зависят типы фронтенда).
- **Разные схемы ответов для ученика, менеджера и владельца.** Не «скрывайте поля», а не включайте их в схему. Приватные поля (`lesson_price`, `price_snapshot`, `is_billable`, `teacher_notes`, финансы) не должны попадать в схемы ученика и менеджера.
- Списки с пагинацией. Для чужих данных ученика отвечайте 404.
- Сессии: серверные, в Redis, cookie `HttpOnly; Secure; SameSite=Lax`. Токены приглашений и входа хранятся только как SHA-256 хэш, одноразовые, с TTL.
- `initData` Telegram валидируется на сервере (HMAC, срок ≤ 24 часа).
- Загрузки файлов: проверка размера, MIME и расширения, имя в S3 — UUID, чтение только по presigned URL.
- После изменения контракта API обязательно обновите `08_api_spec.md`.

### A7. Тексты бота
Все тексты бота и ошибок на стороне бэкенда — в `src/core/texts.py`. Язык — русский.

## Часть B. Фронтенд (TypeScript + React)

Подробности и примеры — `12_frontend_guide.md`. Здесь — обязательные правила.

### B1. Язык и типы
- Только **TypeScript** в режиме `strict`. **Запрещены:** `any`, `// @ts-ignore`, `// @ts-nocheck`, неявные `any`. Приведение типов через `as` допустимо только с комментарием, почему это безопасно.
- Типы данных API **не пишутся вручную**: берутся из `src/api/schema.d.ts`, который генерируется командой `pnpm gen:api`. Файл не редактируется вручную.
- Не используйте сложные типовые конструкции (conditional/mapped types, сложные дженерики) без необходимости. Пишите просто и явно.
- Массивы: помните, что `array[0]` может быть `undefined` (включён `noUncheckedIndexedAccess`).

### B2. Структура и разделение ответственности
- Код организован по возможностям (`features/<имя>/`), общие компоненты — в `components/common/`, базовые UI — в `components/ui/` (shadcn).
- Запросы к API **только** в `features/*/api.ts` через клиент `src/api/client.ts` и `unwrap`. Прямой `fetch` допускается только для загрузки файлов (там же).
- Данные с сервера — **только TanStack Query**. Не загружайте данные в `useEffect`. Глобальные хранилища (Redux, Zustand) не добавлять.
- Фронтенд **не содержит бизнес-правил**: проценты, конвертация баллов, заработок, дедлайны, «просрочено», лимит переносов вычисляет бэкенд. Фронтенд только отображает.
- Права проверяет сервер. Скрытие кнопок на фронтенде — только удобство.
- Экспорт именованный (`export function X`). `export default` только для страниц, подключаемых через `React.lazy`.
- Один компонент = один файл, имя файла совпадает с именем компонента.

### B3. Интерфейс
- **Тексты** — только в `src/lib/texts.ts`. Язык — русский.
- **Цвета, отступы, радиусы, шрифты** — только через токены (`styles/tokens.css`, классы Tailwind вида `bg-primary`). Hex-цвета в компонентах запрещены.
- **Дизайн:** если `07_design.md` заполнен, **ориентируйтесь только на него** и не отклоняйтесь. Если не заполнен, используйте минималистичные нейтральные токены по умолчанию и не тратьте время на оформление.
- Mobile-first. Админка дополнительно имеет десктопный вид. Проверяйте ширины 360 и 1280 px.
- Каждый экран с данными обрабатывает состояния: **загрузка (скелетон), ошибка (с «Повторить»), пусто, данные, отправка** (кнопки блокируются на время запроса).
- Время форматируется только через `src/lib/datetime.ts` в часовом поясе пользователя (`me.timezone`). Не использовать методы `Date`, зависящие от пояса устройства.
- Статусы отображаются только через `StatusBadge`.
- Доступность: нажимаемые области ≥ 44 px, у иконок-кнопок `aria-label`, смысл не только цветом.
- Интеграция с Telegram изолирована в `src/lib/telegram.ts`; остальной код SDK Telegram не импортирует. Внешние скрипты с адресов вне нашего домена не подключаются.

### B4. Формы
- `react-hook-form` + `Zod`. Клиентская валидация — для удобства, сервер проверяет окончательно.
- Ошибки сервера (коды из `08`) показываются понятным текстом из `texts.ts`.

### B5. Безопасность фронтенда
- Никаких секретов в коде и `VITE_*` переменных.
- Запрещён `dangerouslySetInnerHTML`. Пользовательский текст выводится только как текст.
- Внешние ссылки открываются только при `https://` и с `rel="noopener noreferrer"`.
- В консоль и Sentry не попадают `initData`, токены и персональные данные.

### B6. Комментарии и пояснения (важно для проекта)
- Комментарии на русском. Поясняйте **почему**, а не «что делает строка».
- Для нетривиальных конструкций React/TypeScript (хуки, ключи кеша, инвалидация запросов) оставляйте короткий комментарий-подсказку, потому что владелец проекта не знаком с JS/TS.
- В описании выполненной работы (в конце ответа) кратко объясняйте, какие файлы созданы и зачем, простыми словами.

### B7. Тесты фронтенда
- Vitest + Testing Library, API подменяется через MSW.
- Обязательно: `lib/datetime.ts`, `unwrap`/ошибки, `RequireRole`, формы с границами значений, экран ДЗ ученика по состояниям, отсутствие финансовых данных в экранах ученика и менеджера.
- Playwright — после ядра MVP.

## Часть C. Тесты бэкенда
- `pytest`, `pytest-asyncio`, `testcontainers` (PostgreSQL, Redis).
- Каждая функция бизнес-логики имеет тест. Обязательно на MVP: права доступа (включая негативные кейсы), генерация расписания (идемпотентность, горизонт, правка шаблона), пересечения уроков, перенос дедлайна ДЗ (лимит 2), `expired`, конвертация баллов (4 шкалы, правило геометрии ОГЭ), снимок цены, формулы заработка и статистики, тихие часы и дедупликация уведомлений, приглашения (одноразовость, TTL, перепривязка), сессии и валидация `initData`.
- Внешние сервисы (Telegram, S3) мокаются. Время контролируется (`time-machine`).
- Тест контракта: схемы ответов ученика и менеджера не содержат запрещённых полей.

## Часть D. Порядок разработки нового модуля
1. Обновить документацию, если меняются правила или данные.
2. Модели SQLAlchemy → миграция Alembic.
3. Схемы Pydantic (`schemas/`).
4. Репозитории → сервисы (+ тесты).
5. REST-эндпоинты (`api/`) и/или хэндлеры бота (`bot/`); обновить `08`.
6. Задачи воркера, если нужны.
7. Запустить бэкенд, выполнить `pnpm gen:api`.
8. Фронтенд: хуки `api.ts` → компоненты → страница → маршрут → тексты → состояния (+ тесты).
9. Сверить с `07_design.md` (если заполнен).
10. Пройти Definition of Done.

## Часть E. Definition of Done
Задача выполнена, только если:
- [ ] Бэкенд: `ruff check`, `ruff format --check`, `mypy --strict`, `pytest` — зелёные.
- [ ] Фронтенд: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build` — зелёные; `schema.d.ts` актуален.
- [ ] Миграция создана, применяется и откатывается.
- [ ] Нет хардкода секретов; `.env.example` обновлены.
- [ ] Права доступа проверены на сервере и покрыты тестом.
- [ ] Схемы ответов для ученика/менеджера не содержат приватных полей.
- [ ] Тексты вынесены (`texts.py` / `texts.ts`).
- [ ] Обработаны состояния интерфейса (загрузка, ошибка, пусто, отправка).
- [ ] Нет блокирующего I/O и N+1 запросов в добавленном коде.
- [ ] Документация обновлена, если менялись правила, данные или эндпоинты.
- [ ] Реализовано только то, что описано в документации.

## Часть F. Чего агент делать не должен
- Придумывать сценарии, поля, роли, статусы.
- Добавлять зависимости или менять стек без согласования.
- Писать SQL-запросы вне `repositories/`; делать `commit` в репозиториях.
- Менять шкалы экзаменов в коде.
- Возвращать финансовые данные в ответах для ученика и менеджера.
- Дублировать бизнес-логику во фронтенде.
- Использовать `any`, `@ts-ignore`, `dangerouslySetInnerHTML`, `localStorage` для чувствительных данных.
- Добавлять платежи, баланс занятий, должников, воронку заявок: это осознанно вне проекта.

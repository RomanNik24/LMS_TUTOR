# 0003. Единый подход к ENUM (T0.04)

- **Статус:** Принято (текущий стандарт; **подтверждено владельцем 2026-10-06**)
- **Дата:** 2026-10-06
- **Задача:** T0.04 (`docs/PLAN_FROM_SCRATCH.md`)
- **Контекст:** `docs/04_database_schema.md` §0 (строка про Enum) допускает два варианта — нативные PostgreSQL ENUM либо `VARCHAR` + `CHECK` — и требует выбрать **один** единый подход при старте и держаться его. Схема содержит десятки полей-статусов (`role`, `purpose`, `status`, `attendance`, `kind`, `due_mode`, `submission_type`, …), часть которых по roadmap будет меняться (добавление значений статусов).
- **Решение:**
  - Используем **`VARCHAR` + `CHECK`**: в SQLAlchemy — `Enum(native_enum=False)` (либо `String` + `CheckConstraint`), значения задаются в `src/core/enums.py`.
  - **Обоснование:**
    - Alembic-дружелюбно: добавление/изменение значений статуса = правка CHECK-ограничения через обычную миграцию с рабочим `downgrade`. Нативный PostgreSQL ENUM требует `ALTER TYPE … ADD VALUE`, который трудно выполнять внутри транзакции миграции, и заметно сложнее откатывать.
    - Та же защита от «мусорных» значений на уровне БД, что и у нативного ENUM.
    - Совместимо с уже заданными в `docs/04` CHECK-ограничениями (цены, баллы, `weekday`, `extensions_count` и т.д.) и с `alembic autogenerate`.
  - **Решение пересматриваемо:** владелец может пересмотреть выбор **до реализации БД** (задача T1.02). До этого момента все модели/миграции следуют `VARCHAR` + `CHECK`.
- **Последствия:** `src/core/enums.py` объявляет значения; модели держат колонки как строки с CHECK; миграции не используют нативные типы `ENUM` PostgreSQL; в OpenAPI-схемах значения статусов остаются строками.

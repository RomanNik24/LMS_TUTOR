# 09. Безопасность и защита данных

## 1. Модель угроз (кратко)
| Угроза | Мера |
|---|---|
| Чужой человек получает доступ к аккаунту ученика | Одноразовые ссылки-приглашения с TTL, привязка к `telegram_id`, отзыв, перепривязка только по подтверждению |
| Подделка запросов Mini App | Обязательная проверка `initData` (HMAC) на сервере |
| Перебор токенов | Длинные случайные токены (256 бит), хранение только хэша, rate limiting |
| Ученик читает чужие данные | Проверка владения в каждом сервисе, DTO без приватных полей |
| Ученик видит цены/финансы | Поля отсутствуют в DTO ученика; тесты на утечки |
| Менеджер видит финансы | Разграничение по ролям в сервисах и UI |
| Утечка секретов | Только `.env` и GitHub Secrets, `.env` в `.gitignore`, проверка pre-commit |
| Вредоносные файлы | Ограничение типов и размера, переименование в UUID, приватный бакет, presigned URL |
| Потеря данных | Ежедневные бэкапы, проверка восстановления |
| Подмена вебхука | Секретный путь + заголовок `X-Telegram-Bot-Api-Secret-Token` |
| XSS (вредоносный текст в комментариях, описаниях) | React экранирует вывод; `dangerouslySetInnerHTML` запрещён; строгий `Content-Security-Policy`; cookie `HttpOnly` |
| CSRF | `SameSite=Lax`, проверка `Origin` и заголовка `X-Requested-With` на изменяющих запросах |
| «Сгорание» ссылки входа при предпросмотре мессенджером | Токен погашается только POST-запросом со страницы входа |
| Зависимость фронтенда от внешних адресов, недоступных из РФ | Скрипты, шрифты и картинки отдаются с нашего домена |
| Уязвимости в npm-зависимостях | `pnpm-lock.yaml`, `pnpm audit` в CI, ежемесячное обновление |

## 2. Аутентификация

### 2.1. Приглашения
- Токен: `secrets.token_urlsafe(32)`. В БД только `SHA-256(token)`.
- Ссылка: `https://t.me/<bot>?start=inv_<token>`.
- Одноразовая. TTL 7 дней. Новое приглашение для того же пользователя отзывает прежние.
- Принятие привязывает `telegram_id`. Если у профиля уже есть другой `telegram_id` — только после явного подтверждения. Если `telegram_id` занят другим профилем — отказ.

### 2.2. Mini App
- Фронтенд читает `initData` из параметров запуска и отправляет `POST /api/v1/auth/telegram`. Сервер проверяет подпись по токену бота и `auth_date` (не старше 24 часов), находит пользователя по `telegram_id`, создаёт серверную сессию (Redis) и ставит cookie.
- Права определяются по записи в БД, а не по данным клиента. Роль, которую «знает» фронтенд, используется только для навигации.

### 2.3. Браузер
- `/web` в боте → ссылка `https://<домен>/login/<token>` (`web_login`, TTL 10 минут, одноразовая). Страница показывает кнопку «Войти», токен погашается **только POST-запросом** `POST /api/v1/auth/link`. Так мессенджеры и антивирусы не «сжигают» токен предпросмотром ссылки.
- Сессия хранится **на сервере (Redis)**; в браузер уходит только случайный идентификатор в cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`). JavaScript не имеет доступа к cookie, токенов во фронтенде нет.
- Срок жизни сессии: 30 дней неактивности для ученика, 7 дней для персонала. Выход (`POST /auth/logout`) удаляет сессию на сервере.
- Архивирование пользователя, смена `telegram_id` или смена роли удаляют все его сессии.

### 2.3.1. Защита от CSRF
- Cookie `SameSite=Lax`.
- Изменяющие запросы (`POST/PATCH/PUT/DELETE`) обязаны иметь заголовок `X-Requested-With: XMLHttpRequest` и допустимый заголовок `Origin` (наш домен); иначе 403.
- Фронтенд и API на одном домене, CORS не включается.

### 2.4. Пароли
Не используются. Вход по паролю не реализуется.

## 3. Авторизация
- Роли: `student`, `manager`, `owner`. Матрица — `08_api_spec.md`.
- Проверка в сервисах (`require_role`, `ensure_owns_resource`), а не только в интерфейсе.
- Каждый тест прав включает негативные кейсы (ученик → чужие данные, менеджер → финансы).

## 4. Защита данных
- Транспорт: только HTTPS (Let's Encrypt). HSTS на Nginx.
- БД и Redis недоступны снаружи (только внутренняя сеть Docker).
- Бакет S3 приватный. Доступ к файлам по presigned URL (TTL 5–15 минут).
- Логи без персональных данных (используем `user_id`). Sentry: отключить отправку PII (`send_default_pii=False`), фильтровать токены и `initData`.
- Бэкапы шифруются на стороне хранилища (или `gpg`), доступ ограничен.
- Резервные копии и логи не хранятся дольше установленных сроков (бэкапы 14 дней).
- Фронтенд: Sentry без PII, из URL перед отправкой удаляются токены; в консоль не выводятся `initData` и персональные данные.
- Минимизация данных: хранится только необходимое (имя, класс, Telegram ID, результаты). Контакт родителя необязателен.

## 5. Секреты
- Список (бэкенд): `BOT_TOKEN`, `WEBHOOK_SECRET`, `SESSION_SECRET`, `DATABASE_URL`, `REDIS_URL`, `S3_*`, `SENTRY_DSN`.
- Фронтенд секретов **не содержит**: в `VITE_*` попадают только публичные значения (имя бота, адрес API, публичный DSN Sentry).
- Хранение: `.env` на сервере (права 600), GitHub Secrets для CI/CD.
- Ротация: при подозрении на утечку (перевыпуск токена бота в BotFather, очистка всех сессий в Redis и смена `SESSION_SECRET` — разлогинит всех).
- Репозиторий **public** на время разработки (`docs/ops/REPO_SETTINGS.md` §4, ADR 0006); в pre-commit проверка на секреты (gitleaks). Перед загрузкой **реальных данных учеников** репозиторий переводится в **private** (плановая задача T9.01).

## 6. Аудит
`audit_log` фиксирует чувствительные действия (список в `04`, п. 7.2). Доступен владельцу.

## 7. Персональные данные и закон (после MVP)
Ученики находятся в РФ, часть — несовершеннолетние. На этапе MVP юридическое оформление не блокирует разработку, но **должно быть выполнено до запуска для широкого круга пользователей**. Технические решения уже учитывают требования:

**Технически заложено:**
- Размещение БД и файлов на серверах в РФ.
- Минимизация состава данных.
- Журнал аудита, контроль доступа, шифрование каналов.
- Возможность архивации и удаления данных ученика по запросу (процедура ручная в MVP).

**Чек-лист для владельца (самозанятый) — выполнить позже, при необходимости проконсультироваться с юристом:**
- [ ] Определить, является ли деятельность обработкой ПДн как оператора (152-ФЗ) и нужно ли уведомление Роскомнадзора.
- [ ] Подготовить политику обработки ПДн и опубликовать на сайте/в боте.
- [ ] Получить согласие на обработку ПДн: от совершеннолетних — лично, от несовершеннолетних — от законного представителя.
- [ ] Назначить порядок обработки обращений (доступ, исправление, удаление данных).
- [ ] Зафиксировать места хранения и сроки хранения данных.
- [ ] Учесть, что бот использует инфраструктуру Telegram (трансграничная передача) и описать это в политике.
- [ ] При внедрении сторонних сервисов (Sentry и др.) оценить, какие данные уходят за рубеж; по возможности использовать самохостинг или отключить отправку ПДн.

> Это справочный чек-лист, а не юридическая консультация.

## 8. Обработка инцидентов
1. Подозрение на утечку → отозвать все приглашения и сессии (очистка сессий в Redis, смена `SESSION_SECRET`), перевыпустить токен бота.
2. Проверить `audit_log` и логи доступа Nginx.
3. Уведомить владельца и затронутых пользователей.
4. Зафиксировать причину, исправить, добавить тест.
